# Experiment 2 — Server queue policies against the retry loop

Lab Exame CSC-27 / CE-288 · ITA · November 2026
João Guerreiro · Lucas de Sousa · Marcelo Hippolyto · Pablo Carvalho · Advisor: Prof.ª Juliana de Melo Bezerra

When clients retry after a timeout, a transient slowdown can leave a service stuck after the cause is gone: its workers stay busy on requests nobody is waiting for any more (a *metastable failure*). This experiment compares four server queue policies (fixed queue, fixed time bound, per-request deadline, adaptive LIFO) under two client retry policies (fixed delay, exponential backoff with jitter), at four loads, to see which ones let the service recover.

## Running it

Requirements: Docker with Compose (the standalone `docker-compose` or `docker compose`). Nothing else runs on the host: Go, k6, Python, Postgres and Prometheus all run in containers.

```sh
./bancada.sh testes                                  # build the images; the unit tests run inside the build
caffeinate -dimsu ./experimentos.sh                  # macOS, on AC power: calibration + 96 runs + analysis, about 4 h 30
./experimentos.sh                                    # Linux
```

Faster, partial runs:

```sh
./bancada.sh calibrar                                         # measure capacity μ and service time Ŝ
./bancada.sh varredura -nome principal -reps 1                # one run per configuration (32 runs, about 1 h 30)
./bancada.sh cenario -fila lifo -politica fixed -carga 70     # a single run
./bancada.sh analise --varredura principal                    # tables and figures from the data
./bancada.sh derrubar                                         # remove the containers
```

An interrupted sweep can be resumed with the same command: runs that already have a `manifesto.json` are reused.

On a laptop, keep it plugged in with the lid open and the display on. On battery, or with the display off, macOS slows the virtual machine down. The orchestrator detects freezes and missing samples, and discards and repeats the affected run.

## Output

Everything goes to `resultados/` (created by the run):

| Path | Content |
|---|---|
| `calibracao.json` | μ, Ŝ and their reliability checks |
| `principal/execucoes/<id>/series.csv` | one line per second for each run: client and service counters, per class and per drop reason |
| `principal/execucoes/<id>/manifesto.json` | the exact configuration of the run, real fault instants, software versions, and summary |
| `principal/resumo.csv` | one line per run |
| `tabelas_principal.md`, `figuras/` | tables and figures generated by the analysis |

## Folder map

| Path | What it is |
|---|---|
| `servidor/` | Service under test (Go): 8 workers, 64-slot queue, the four queue policies, switchable at runtime through `POST /admin/policy` |
| `cliente/script.js` | Load generator (k6): open-loop arrivals, two client timeout classes, both retry policies |
| `orquestrador/` | Orchestrator (Go): calibration, sweep, fault injection, series export, measurement guards |
| `infra/` | Postgres, Toxiproxy (fault injection) and Prometheus images |
| `analise/` | Analysis (Python): tables and figures; `estatistica.py` aggregates the repetitions |
| `modelo-matematico/` | Closed-form model and simulator (Python, standard library only) |
| `docker-compose.yml` | The bench |
| `bancada.sh` | Wrapper for every command above |
| `experimentos.sh` | The whole campaign in one command |

Code comments, log messages and generated tables are in Portuguese; the documents are in English.
