## 1. Summary

1. **Fixed queue (baseline):** gets stuck from 50 % load on, with both clients, as in experiment 1. At 90 % it collapses on its own, before any fault is injected.
2. **Fixed time bound (W = 98 ms):** fails for the impatient clients from 70 % load on. A single bound sized for the mean timeout lets requests with a 100 ms timeout wait too long, so they are processed after their client has given up. The impatient class ends with 0–3 % of requests answered in time while the patient class is still served. In 3 of its 4 runs at 70–90 %, the system collapsed before the fault.
3. **Per-request deadline:** recovered in 0–1 s in all 8 runs, with about 100 % of both classes answered in time and practically no wasted work.
4. **Adaptive LIFO:** recovered in 0 s in all 8 runs. Its overload detector was on for 90–100 % of every fault. Its cost when nothing is wrong is the highest of the four at 90 % load.
5. **Fixed delay vs backoff with jitter:** made no difference to whether the service recovered. Only the moment the fixed time bound broke changed.

### 3.1 Fixed queue: the loop closes, as in experiment 1

| Client | Load | Answered in time at end | Amplification at end | Wasted work at end (req/s) | p99 in service (ms) |
|---|---:|---:|---:|---:|---:|
| fixed delay | 50 % | 0.0 % | 4.00 | 194.5 | 399 |
| fixed delay | 70 % | 0.0 % | 4.00 | 194.4 | 399 |
| backoff | 50 % | 0.7 % | 4.04 | 183.7 | 686 |
| backoff | 70 % | 0.0 % | 4.02 | 195.3 | 399 |

Once the fault starts, every new request turns into 4 attempts (1 + 3 retries), the queue stays full, and the 8 workers spend their whole capacity (about 190 req/s) on requests whose clients have already given up. At 90 % load, both runs collapsed 28 s into the run, during steady state and before any fault. This is the "vulnerable" state seen in experiment 1: an ordinary burst is enough to trip the loop. At 20 %, below the 1/(N + 1) = 25 % frontier, the fixed queue recovers in 0 s.

### 3.2 Fixed time bound: the impatient class gets stuck

Per client class (fraction answered in time over the last 30 s, and wasted work):

| Client | Load | Outcome | Impatient answered | Patient answered | Impatient wasted (req/s) | Patient wasted (req/s) |
|---|---:|---|---:|---:|---:|---:|
| fixed delay | 20 % | recovered | 100.1 % | 99.9 % | 0.0 | 0.0 |
| fixed delay | 50 % | recovered (94.7 % overall) | **89.6 %** | 100.0 % | 16.6 | 0.3 |
| fixed delay | 70 % | collapsed at 13 s | **3.4 %** | 76.3 % | 139.8 | 0.1 |
| fixed delay | 90 % | collapsed at 9 s | **2.3 %** | 64.2 % | 133.0 | 0.3 |
| backoff | 20 % | recovered | 100.2 % | 100.2 % | 0.1 | 0.1 |
| backoff | 50 % | recovered | 100.0 % | 100.1 % | 0.0 | 0.0 |
| backoff | 70 % | stuck after the fault | **0.4 %** | 93.2 % | 134.6 | 0.0 |
| backoff | 90 % | collapsed at 28 s | **0.1 %** | 82.5 % | 123.6 | 0.0 |

W = 98 ms is the right bound for a client with a 150 ms timeout, but this policy uses it for everyone:

- **Impatient clients (100 ms timeout)** can afford at most 48 ms of waiting. The policy lets their requests wait up to 98 ms, process them, and finish them after the client has left. That wasted work, 120–140 req/s, is the same amplifier as in the fixed queue, now confined to the impatient class.
- **Patient clients (200 ms timeout)** are mostly still served, because their requests usually fit within W.

The policy fixes the problem for the clients whose timeout matches W and keeps it for the rest. With the fixed-delay client it broke even without the fault (collapses at 9 s and 13 s); with backoff, the fault was needed at 70 %, but not at 90 %.

|---|---:|---:|---:|---:|---:|---:|---:|
| fixed delay | 20 % | 0 s | 100.0 % | 100.1 % | 0.0 | 0.18 | 0 |
| fixed delay | 50 % | 0 s | 100.0 % | 100.0 % | 0.0 | 0.65 | 0 |
| fixed delay | 70 % | 0 s | 100.0 % | 100.1 % | 0.0 | 2.19 | 0 |
| fixed delay | 90 % | 0 s | 100.2 % | 100.2 % | 0.0 | 0.85 | 0 |
| backoff | 20 % | 0 s | 100.1 % | 100.0 % | 0.0 | 0.00 | 0 |
| backoff | 50 % | 0 s | 100.0 % | 100.1 % | 0.0 | 0.40 | 0 |
| backoff | 70 % | 0 s | 100.1 % | 100.1 % | 0.3 | 2.96 | 0 |
| backoff | 90 % | 0 s (impatient: 1 s) | 99.9 % | 100.1 % | 0.1 | 3.05 | 0 |

Because the server knows each request's own deadline, it never starts work that cannot finish in time. Wasted work stays near zero, so the loop has nothing to feed on. This holds in both classes and at every load. The cost when nothing is wrong is at most 3 drops per second in steady state, out of 38–172 new requests per second. Fractions slightly above 100 % come from requests started just before a 30 s window and answered inside it.

### 3.4 Adaptive LIFO: recovers everywhere, with a visible detector

| Client | Load | Recovery | LIFO on in steady state | LIFO on during fault | LIFO on at end | Drops in steady state (req/s) | Needless drops in steady state, patient (req/s) |
|---|---:|---:|---:|---:|---:|---:|---:|
| fixed delay | 20 % | 0 s | 3.3 % | 90 % | 0 % | 0.11 | 0.03 |
| fixed delay | 50 % | 0 s | 0 % | 100 % | 0 % | 0.87 | 0.20 |
| fixed delay | 70 % | 0 s | 0 % | 100 % | 3.3 % | 1.82 | 0.45 |
| fixed delay | 90 % | 0 s | 6.7 % | 100 % | 20.0 % | 3.07 | 1.55 |
| backoff | 20 % | 0 s | 0 % | 95 % | 0 % | 0.00 | 0.00 |
| backoff | 50 % | 0 s | 0 % | 100 % | 0 % | 0.77 | 0.13 |
| backoff | 70 % | 0 s | 6.7 % | 100 % | 3.3 % | 3.23 | 1.12 |
| backoff | 90 % | 0 s | 16.7 % | 100 % | 13.3 % | 12.39 | 6.34 |

- **Detector:** it works. It was on for 90–100 % of every fault and switched off as the queue emptied. At 90 % load it also switches on briefly in normal operation (up to 17 % of seconds), when bursts keep the queue busy for more than 100 ms.
- **Cost:** those short switches have a price. At 90 % with backoff, LIFO dropped 12.4 req/s in steady state, and 6.3 req/s of those were patient requests that could still have finished in time (evicted or expired with W = 98 ms). This is the highest steady-state cost of any policy that recovered: policy 3 had 3.05 drops per second and no needless drops at the same load.
- **Admission rule:** it never refused an arrival for a full queue (0 "full" drops). All its drops were evictions of the oldest request or purges of stale ones, as designed.

### 3.5 Client retry policy

Within each queue policy, the two clients led to the same recovery outcome at every load, except for the fixed time bound at 70 %: with the fixed-delay client the system collapsed during steady state, and with backoff it got stuck only after the fault. Backoff with jitter delays retries but does not reduce how many there are. This repeats the conclusion of experiment 1 at the client side: what moves the outcome is the server's queue policy, not the spacing of retries.

## 6. Conclusions

1. **The queue policy decides whether the service recovers.** With the same clients, the same load and the same fault, the fixed queue stays stuck and the per-request deadline and adaptive LIFO recover within a second.
2. **A time bound must match the client's own timeout.** A single bound sized for the average client fails the clients with shorter timeouts. It reproduces the metastable loop inside that class, and can even trigger it without a fault. Passing the deadline with the request (policy 3) removes the problem, with no needless drops.
3. **Adaptive LIFO works, but costs more under high load.** Its overload detector reliably catches the fault. At 90 % load, normal bursts also trip it, and the evictions plus the fixed W cost some patient requests that would have been served.
4. **Backoff with jitter on the client does not replace a server-side policy.** It did not change whether the service recovered in any of the 4 policies.
5. **On this bench, the per-request deadline was the best single policy.** It recovered in every configuration, had the lowest steady-state cost, and had no needless drops.

## 7. Limitations

- **One run per configuration** (repetition 1). The results show the pattern, not its variability. The 2 extra repetitions will show whether, for example, the fixed time bound fails at 50 % in some runs, or LIFO fails at 90 %.
- **One machine, one fault type, nearly constant service time** (p95 within 3 ms of the mean). A service with more variable service times would make the deadline check based on Ŝ less accurate.
- **"Recovered" and "stuck" refer to the 90 s observed after the fault.**
- **Untuned parameters.** W was set by rule (mean timeout − Ŝ − margin), not tuned. A fixed bound sized for the shortest timeout would have protected the impatient clients, at the cost of dropping more patient requests.
